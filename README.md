# Lights Out (Погаси свет)

Браузерная версия классической головоломки «Lights Out». Делали её как лабораторную работу по дисциплине «Технологии разработки программно-информационных систем».

## Об игре

Перед игроком поле 5×5. Каждая клетка либо горит, либо нет. Клик по клетке переключает её саму и четырёх соседей (сверху, снизу, слева и справа). Задача — погасить всё поле.

Что есть в игре:

* **15 уровней.** На каждом уровне минимальное число ходов для решения ровно равно номеру уровня: первый решается за 1 ход, пятнадцатый — за 15.
* **Генерация уровней.** Поле получается «обратным ходом»: берём эталонное минимальное решение из 15 клеток и применяем к пустому полю первые N ходов. Поэтому короче, чем за N ходов, уровень не решить.
* **Конец игры.** После 15-го уровня поле блокируется и появляется надпись «Вы победили!». Начать заново можно кнопкой «Перезапустить игру».
* **Только клиент.** Сервер, база данных и интернет не нужны: всё работает в браузере.

## Как запустить

Код разбит на ES-модули, а браузер не загружает их, если открыть `index.html` двойным кликом (адрес `file://`). Нужен любой локальный сервер. Проще всего через Python, из папки проекта:

```bash
python -m http.server 8000
```

После этого:

* игра — http://localhost:8000/
* тесты — http://localhost:8000/tests/

Подойдёт и расширение Live Server для VS Code.

## Как мы оформляем коммиты

Одно логическое изменение — один коммит. Сообщение пишем по-русски, в прошедшем времени, то есть что сделано, а не что надо сделать. Формат: `<тип>: <описание>`.

* `feat:` — новая функциональность
* `fix:` — исправление бага или опечатки
* `refactor:` — переработка кода без изменения поведения
* `test:` — тесты
* `docs:` — только документация
* `chore:` — служебное (настройки репозитория, `.gitignore`)

Например:

* `feat: реализован алгоритм обратного хода для генерации уровней`
* `docs: добавлен раздел про завершение игры в SRS`
* `chore: обновлен .gitignore`

Сообщения вроде `update`, `fix`, `правки`, `asdf` или просто `тест` не принимаются.

## Ветки и ревью

Работаем по feature branching. Стабильная версия лежит в `main`, и напрямую туда пушить нельзя: ветка защищена на GitHub. Сливает изменения в `main` только тимлид.

Как проходит работа над задачей:

1. Обновить локальный `main`.
2. Создать от него ветку под задачу, например `feature/level-generation` или `fix/ui-bug`.
3. Делать задачу, коммитя по ходу отдельные шаги.
4. Запушить ветку на GitHub.
5. Подтянуть свежий `main` в свою ветку и решить конфликты, если они есть.
6. Открыть Pull Request и назначить ревьюера: тимлида или кого-то из команды.
7. Если есть замечания, исправить их и обновить ветку.
8. Тимлид проверяет, что всё работает и конфликтов нет, и сливает ветку в `main`.
9. Удалить отработавшую ветку. Следующая задача начинается с новой ветки от `main`.

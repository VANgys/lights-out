# Lights Out (Погаси свет)

Классическая логическая головоломка, реализованная в виде клиентского веб-приложения.
Проект выполнен в рамках лабораторных работ по дисциплине «Технологии разработки программно-информационных систем».

## Об игре

«Lights Out» — это 2D-головоломка с видом сверху. Игровое поле представляет собой квадратную сетку размером 5×5, каждая клетка которой может находиться в состоянии «включено» (подсвечена) или «выключено» (не подсвечена).
При клике на клетку инвертируется её состояние и состояние всех ортогональных соседей (вверх, вниз, влево, вправо).
**Цель игры** — погасить все клетки на поле (привести их в состояние «выключено»).

### Особенности игры:
* **15 уровней сложности.** Минимальное количество ходов для решения уровня строго равно номеру уровня.
* **Умная генерация.** Уровни генерируются с помощью алгоритма «обратного хода» на основе эталонных минимальных решений, что гарантирует отсутствие более коротких путей решения.
* **Завершение игры.** После прохождения 15-го уровня игровое поле блокируется, и отображается сообщение о победе.
* **Чистый клиент.** Игра работает полностью в браузере, не требует серверной части и подключения к интернету (после загрузки).

## Правила формирования коммитов

Одно логическое изменение — один коммит. Сообщения пишутся на русском языке в прошедшем времени (что было сделано, а не что *надо сделать*). Формат: `<тип>: <краткое описание>`

*   `feat:` — добавление новой функциональности.
*   `docs:` — изменения, касающиеся только документации (текст, Markdown).
*   `test:` — добавление или обновление тестов.
*   `refactor:` — переработка кода без изменения его поведения.
*   `fix:` — исправление багов в коде, опечаток в интерфейсе или логических ошибок.
*   `chore:` — служебные задачи (настройка репозитория, `.gitignore`).

**Допустимые примеры:**
*   `feat: реализован алгоритм обратного хода для генерации уровней`
*   `docs: добавлен раздел про завершение игры в SRS`
*   `chore: обновлен .gitignore`

**Недопустимые сообщения:**
*   `update`, `fix`, `правки`, `asdf`, `тест` (без контекста и смысла).

## Ветки и ревью

Работа ведется по стратегии Feature Branching (ветвление по задачам): основная стабильная версия хранится в ветке `main`. Прямая запись в `main` запрещена средствами защиты ветки на стороне GitHub. Включение изменений в `main` выполняется только тимлидом.

Работа над каждой задачей (или пользовательской историей) выполняется по следующей последовательности:
* Обновление локальной ветки `main` до актуального состояния.
* Создание новой рабочей ветки от актуальной версии `main` под конкретную задачу (например, `feature/level-generation` или `fix/ui-bug`).
* Выполнение задачи с фиксацией промежуточных результатов отдельными коммитами.
* Отправка рабочей ветки в удалённый репозиторий.
* Включение актуальных изменений из `main` в рабочую ветку и разрешение возможных конфликтов.
* Создание Pull Request и проведение ревью: назначается ревьюер (тимлид или другой участник команды для перекрестной проверки).
* При наличии замечаний – их устранение автором и обновление ветки.
* Слияние рабочей ветки с `main` выполняется тимлидом после проверки работоспособности и отсутствия конфликтов.
* Удаление отработавшей рабочей ветки (следующая задача начинается с созданием новой ветки от `main`).

## Как проверить историю

После распаковки архива с репозиторием (убедитесь, что скрытая папка `.git` на месте) историю можно посмотреть командами:

```bash
# Краткая история с визуализацией веток
git log --oneline --graph --all

# Полная история с авторами
git log
```
